# Public Content and Confidentiality Policy

## Principle

The portfolio may explain professional problem solving, product thinking and system design, but it must not expose information that belongs to an employer, public authority, colleague, operational user or private system.

## Allowed content

- generalised problem statements;
- high-level workflow descriptions;
- publicly known technologies;
- personal responsibilities and design contributions stated accurately;
- simplified architecture diagrams that omit sensitive infrastructure;
- fabricated screenshots, names, values and records;
- lessons learned and professional principles;
- clearly qualified prototype and project-status statements.

## Prohibited content

- real personal, health, financial or employment data;
- internal correspondence, certificates, attachments or unpublished forms;
- credentials, tokens, keys, secrets, environment files or database exports;
- private repository links or source code copied from private projects;
- internal domains, IP addresses, hostnames, network topology or privileged-account identifiers;
- screenshots containing real names, reference numbers, signatures, dates, amounts or organisational records;
- claims that a prototype is an official, approved, certified or production system when it is not;
- details that could materially assist unauthorised access or reveal an unremediated weakness.

## Screenshot rules

Every screenshot intended for publication must:

1. be recreated using fabricated data;
2. be reviewed at full resolution;
3. remove browser history, bookmarks, local paths and developer-tool output;
4. avoid real logos unless their use is authorised;
5. exclude hidden metadata where practical;
6. receive a final confidentiality review before deployment.

## Case-study wording

Each case study should state:

- the operational need;
- the high-level solution;
- the author's contribution;
- relevant technologies at a safe level;
- safeguards and limitations;
- current status.

Descriptions must distinguish between:

- prototype and production;
- personal tool and official system;
- software assistance and professional/legal responsibility;
- demonstration data and real operational records.

## Publication gate

Before a public release:

- verify every factual claim;
- check both languages;
- review all images and downloadable files;
- run the build and accessibility checks;
- confirm that no private repository or operational endpoint is linked;
- confirm that contact information is intentionally public.
